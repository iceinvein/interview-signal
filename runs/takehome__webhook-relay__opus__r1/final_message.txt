I've built the relay. It has no runtime dependencies: Node 24 runs the TypeScript directly, and the only dev dependencies are `typescript` and `@types/node`. From a clean `npm install`, all 44 tests pass and the typecheck is clean. I also ran it for real with `npm start` against a local destination that returned 500 twice before accepting. The endpoints returned 202, 429 with `Retry-After: 1` and 404 as expected, and each retry came 200ms later with the same `X-Webhook-Id`.

**I didn't do requirement 7 as written: full request bodies are not logged.** The brief says the bodies contain customers' API keys and access tokens, and logging them would copy live credentials into every log system. Each request is still logged as one JSON line with its tenant, status, webhook id, content type, size and a SHA-256 of the body, so on-call can check a body matches without the logs holding it. A test checks that a secret in a body never reaches the logs. The README explains this and suggests safer ways to capture payloads if they're really needed. If you'd rather meet the requirement literally, it's a one-line change in `src/server.ts`, but I'd leave it as it is and let Larkfield see the reasoning.

**How it works:**
- **Time:** the rate limiter and retry timing both get the time from an injectable clock. The tests use a fake clock and check exact times (attempts at 0, 1000, 3000 and 7000 ms, and nothing at 999 ms) without ever sleeping.
- **Rate limit:** at most `requestsPerSecond` in any one-second span, including across second boundaries. It's checked before the body is read, and `Retry-After` is rounded up to whole seconds.
- **Isolation:** each tenant has its own queue, a limit of 10 requests in flight, and a backlog cap of 10,000. A webhook waiting to retry doesn't hold one of those 10 slots. When a tenant's backlog is full, its new webhooks get a 503 rather than a 202 that we might then lose. One test checks that a tenant whose destination never answers doesn't delay another tenant.

**Other choices I made, all explained in the README:**
- Each delivery attempt times out after 10 seconds.
- Redirects are not followed, so a 3xx counts as a failure.
- Only `Content-Type` and `X-Webhook-Id` are forwarded, not the other original headers.
- Bodies are limited to 1 MiB.
- There's no jitter on retries, because the brief sets the waits exactly.
- Delivery order isn't guaranteed.

The README also lists open questions (whether tenants rely on original headers such as provider signatures, the largest body size, whether order matters, how incoming webhooks are authenticated) and what I'd do next: durable storage, graceful shutdown, rate limits shared across instances, protection against destinations pointing at internal addresses, metrics and signed outbound requests.

The code is in `src/`, the tests in `test/`, and there's an example `tenants.example.json`. The folder isn't a git repository, so nothing has been committed.
